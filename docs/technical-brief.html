01

What this is

Problem statement SIH26076 asks for a personalized homepage for Mausam, IMD's public weather app. Today every user sees the same generic screen.

The brief names eight user types and the data each one needs. Our build reflows the homepage around one to three of those personas, chosen at first launch and editable afterwards, and orders the cards by a rule that can be read out loud.

The eight personas, exactly as the problem statement defines them:

  • Health-conscious — AQI, pollen, UV index, humidity
  • Outdoor fitness — sunrise/sunset, best running hours, wind, heat alerts
  • Beachgoers & surfers — sea state, tide timings, wave height, water temperature
  • Travellers — saved destinations, flight-relevant alerts, packing suggestions
  • Parents & families — school-commute conditions, rain and severe alerts
  • Farmers & gardeners — soil moisture, rainfall, frost alerts, planting guidance
  • Commuters — visibility, fog and storm alerts, road-relevant conditions
  • Event planners — rain probability and a comfort index

Two things the brief does not say out loud but the app's own store reviews do: the current app is slow, and its favourites are unreliable. That set the second bar — the homepage had to be dramatically lighter than what ships today.

02

How the app actually works

A React single-page app served as static files, two serverless functions that hold the secrets, and four keyless feeds the browser is allowed to call directly.

What happens on load, in order

  • Vercel's CDN serves index.html and one JS bundle. MapLibre is not in it.
  • The app renders immediately from data/seed.ts — six cities of demo data. Nothing is blank while the network works.
  • useLiveAqi calls /api/aqi?city=… for the selected city. useLiveWarnings calls /api/warnings once.
  • When either answers, the value is merged into the place object in AppState. Cards, the banner, the advice line and the scoring rules all read the merged place, so nothing else needs wiring.
  • Opening Places lazy-loads the MapLibre chunk. Only then does the browser pay 218 kB for a map.

The one design decision worth defending here: the seeded dataset is not a placeholder waiting to be deleted. It is the floor. If data.gov.in is slow or down during the demo, the card keeps the seeded number and changes its label from live to seeded. The app never shows a blank card or a spinner that never resolves.

03

The stack, and why each piece

Four runtime dependencies. Everything else is a build tool that ships no code to the user.

React 18.3.1
Generally
The most widely used UI library for building interfaces out of components that re-render when their data changes.
Here
Every screen, card and sheet. State lives in one context, AppState, which merges live data into the seeded places.
Why not Vue or Svelte
Both are fine choices. React won on hiring reality — it is what the team already knew, and a hackathon is not the place to learn a framework. Svelte would have produced a smaller bundle.
TypeScript 5.6
Generally
JavaScript with a type checker. Catches mismatched data shapes before the code runs.
Here
The Place type is the contract between seeded data, the CPCB response and every card. Adding a field without deciding where it comes from is a compile error.
Why it earns its cost
The provenance map is exhaustive by type. Forgetting to say whether a reading is live or seeded fails the build rather than shipping a wrong label.
Vite 5.4
Generally
A build tool and dev server. Serves source files natively during development, bundles with Rollup for production.
Here
Dev server, production bundle, code-splitting the map into its own chunk, and a small custom plugin that runs the /api routes locally.
Why not Create React App
CRA is deprecated and its dev server is markedly slower. Vite starts in under a second and its Rollup output is what gives us the lazy map chunk.
Tailwind CSS 3.4
Generally
Utility classes for styling in markup, with unused classes stripped at build time.
Here
Layout and spacing only. Every colour, blur, radius and spring comes from design/tokens.ts instead — one source of truth the build verifies.
Why the split
Contrast has to be computed against real gradients. That is arithmetic, and arithmetic belongs in TypeScript where a script can check it, not in class names.
Framer Motion 11
Generally
An animation library for React with spring physics and automatic layout transitions.
Here
Card enter/exit, FLIP reordering when the score changes, the pull-to-refresh gesture, and the detail sheet.
Why not CSS transitions
CSS cannot animate an element between two layout positions it does not yet occupy. Reordering the stack with a spring is exactly that problem, and layout solves it in one prop.
MapLibre GL JS 4.7
Generally
An open-source vector map renderer. The community fork of Mapbox GL JS from before Mapbox changed its licence.
Here
The map screen: radar tiles, wind tiles, and our own AQI labels drawn over an OpenFreeMap basemap.
Why not Mapbox or Google Maps
Both need an account, a billed key and a usage cap. MapLibre plus OpenFreeMap needs no key at all, which matters for a government app that should not depend on a commercial quota.

What is deliberately not here

Commonly expectedStatusWhy
Expressnot usedVercel functions are plain (req, res) handlers. Express would add a dependency to do routing the platform already does.
TanStack Querynot usedTwo endpoints with different cache rules. Two small hooks are ~90 lines total; the library is larger than the problem.
SQLitenot usedServerless functions have no persistent disk. Caching is an in-memory Map per warm instance plus HTTP cache headers.
Redux / Zustandnot usedOne context with one state object. There is no cross-screen state complex enough to need a store.
An axios-style HTTP clientnot usedGlobal fetch is in Node 18+ and every target browser.

The serverless functions have zero dependencies. They import nothing but Node's own http types. That is why a cold start is fast and why there is no supply chain to audit on the server side.

04

Hosting, and where the backend went

Vercel

Generally: a hosting platform for front-end apps. It builds from a Git push, serves the result from a CDN, and turns files in an api/ directory into serverless functions — small programs that run on demand and shut down after.

Here: it does both jobs. The Vite build output is served statically, and client/api/aqi.ts and client/api/warnings.ts become HTTP endpoints automatically. There is no vercel.json — the layout is detected.

Why Vercel and not Netlify, Render or a VPS

  • Netlify is genuinely comparable and would have worked. Vercel's zero-config detection of a Vite app plus an api/ folder needed no configuration file at all, which is one less thing to be wrong on demo day.
  • Render or a VPS would give a long-running server and a static IP — see below. It also means managing a machine, and a free-tier Render instance sleeps and cold-starts in tens of seconds, which is a bad property for a live demo.
  • GitHub Pages was ruled out immediately: static only, so there is nowhere to hide the CPCB key.

The honest trade-off a judge may find: IMD's own API requires the calling server's IP to be whitelisted. Vercel functions do not have a fixed outbound IP, so this hosting choice rules out ever calling api.imd.gov.in directly. We accepted that because NDMA's Sachet feed republishes the same IMD bulletins with no key and no whitelist. If IMD access is granted for the final build, the backend moves to a fixed-IP host and the two route files move with it unchanged — they are plain Node handlers, not Vercel-specific code.

Why the secret has to sit server-side

Anything Vite inlines into the bundle is public — a user can read it in devtools. Vite only inlines variables prefixed VITE_, so the split is enforced by naming:

VariableWhere it livesWhy
DATA_GOV_KEYServer onlyRegistered to us. In the bundle it could be lifted and used against our quota.
VITE_OWM_KEYIn the bundleOpenWeather map tiles are fetched by the browser and the key is visible in the tile URL by design. Free tier, rate-limited by them.

The same /api files run in development through a custom Vite plugin (vite-plugin-api.ts) that imports them via Vite's SSR loader. It is the same TypeScript file Vercel builds — not a second copy — so a route that works locally works deployed.

Two AQI scales are on screen and that is deliberate. The saved-place cards show CPCB Indian AQI, computed by our own server from raw pollutant concentrations. Caching, and why one TTL would be wrong

CPCB publishes hourly. CAP warnings arrive when they are issued, not on a schedule. Radar refreshes every few minutes. Using one number for all of them would either hammer the upstream or serve stale warnings.

The AQI maths, in full

data.gov.in publishes pollutant concentrations, not an index. The index is computed on our server, using CPCB's published method.

Six pollutants are used: PM2.5, PM10, NO2, SO2, NH3 and ozone. Each has a table of breakpoints mapping a concentration band to an index band. For a reading inside a band, the sub-index is a straight-line interpolation:

Details worth knowing

  • Carbon monoxide is deliberately excluded. CPCB defines CO breakpoints in mg/m³ while the feed publishes µg/m³. Mixing the units would produce a wildly wrong sub-index, and since AQI is a maximum, one wrong sub-index corrupts the whole index.
  • Up to 600 rows per city. Delhi returns roughly 308 rows across 44 stations. An earlier limit of 200 silently truncated it.
  • Station names are exact-match. CPCB files the capital under "Delhi", not "New Delhi" — that mismatch returned zero rows and the card showed seeded data under a live label for the entire life of the feature. Each place now carries an explicit cpcbCity.
  • Kochi has no CPCB station at all. Kerala reports Kannur, Thiruvananthapuram and Thrissur. The card says so rather than inventing a number.
  • The index is capped at 500, as CPCB caps its published figure.
07

The warning pipeline

Severe weather is the one thing in this app that must never be wrong, and it is the one thing that is fully live.

CAP — the Common Alerting Protocol — is an OASIS standard for emergency alerts, used internationally. NDMA publishes India's alerts as CAP 1.2 XML through its Sachet portal, with no key and no whitelisting, and that feed carries the same IMD, state SDMA and Central Water Commission bulletins that IMD's own API would.

What /api/warnings does

  • Fetches the national RSS index (6-second deadline), then fetches individual CAP entries through a 12-way worker pool under a 7-second budget — enough parallelism to enrich the feed without exceeding a serverless invocation.
  • Maps CAP's severity to IMD's public colour code, which happens to be the same four-value shape: Extreme → red Severe → orange Moderate → yellow Minor → green
  • Drops anything not currently in force: status other than Actual, a msgType of Cancel, or an expires time in the past. An expired Chennai bulletin was on screen before this check existed.
  • Matches districts against each saved place using word-boundary Unicode matching. Plain substring matching put a Tamil Nadu thunderstorm on Indore, because "Dhar" appears inside "Dharmapuri".

A live warning is never translated. The app has full Hindi, but a live CAP bulletin is shown exactly as issued. Rewording a real warning would put words in IMD's mouth. Seeded bulletins do carry Hindi, because we wrote them. The rule is applied in one place, i18n/capText.ts, and it covers the headline, the body, the expiry time and the issuing office.

08

How a card earns its place

The problem statement asks for personalization. Ours is arithmetic, not a model — a judge can ask why any card is where it is and get a specific answer with numbers in it.

Three rules the engine also applies

  • Severe warnings outrank everything. The banner is pinned above the persona cards regardless of which personas are active.
  • Suppression is explained, not silent. The beach card cannot show for an inland city, so it is removed and a line below the stack says which persona was suppressed and why.
  • Advice ordering is by consequence, not by data source. Life-safety first, then whatever the active warning is about, then health, then comfort — capped at four items, because a list of nine things to do is a list nobody reads.

Packing suggestions reuse the same engine

The problem statement asks travellers for packing suggestions — "carry a raincoat in London". Rather than write a second rule set, each destination's top advisory is projected onto a thing you can put in a bag: carry an umbrella becomes pack rain cover. Advisories with no honest packing equivalent — "use fog lights", "avoid the underpass" — are absent rather than stretched into one.

09

The design system

One TypeScript file, design/tokens.ts, holds every colour, blur, radius and spring in the app. Nothing is hard-coded in a component.

The sky is a lookup, not a gradient someone picked

The background is a function of two inputs: condition (clear, partly cloudy, overcast, rain, thunderstorm, fog, snow) × time of day (dawn, day, dusk, night). That is 7 × 4 = 28 defined gradients.

Time of day derives from the location's own sunrise and sunset via Intl.DateTimeFormat, not the device clock — so checking Kochi from Delhi shows Kochi's night. Each place carries an IANA timezone for this reason.

Glass, and the contrast problem it creates

Cards are frosted surfaces over that moving background. That is a legibility risk in a severe-weather app, so contrast is not eyeballed — it is computed. A build script composites each glass surface over the real gradient at the screen position where cards actually sit, then measures the WCAG contrast ratio of both text colours against it.

Two glass tiers exist — one for dark skies, one for light — and the app measures which polarity a given sky needs rather than assuming. There is also a flat, blur-free tier for low-end Android, exposed as a toggle, because backdrop-filter is the single most expensive thing on the screen.

Performance

The current app's reviews complain about slow loads. This is the number that answers that.

AssetGzippedWhen

Devanagari font121.2 kBOnly when a Hindi glyph renders

Quote the number carefully. "135 kB" is the JavaScript bundle. A cold first visit in English is closer to 250 kB once the web fonts are counted. Both are good figures for a weather app — but say which one you mean, because a judge with devtools open will see the larger number.

Where the speed comes from

  • The map is deferred. 218 kB of MapLibre is a separate chunk that only downloads when someone opens Places. That is the single biggest win, and it is a deliberate architectural choice rather than a small bundle by luck.
  • Blur is dropped while the stack animates. A transformed backdrop-filter element re-blurs its backdrop every frame; across a stack of cards that is the dominant cost. A short motion window swaps in a flat surface during reorders.
  • Fonts are subset by unicode-range. An English session downloads the Devanagari stylesheet but none of its 121 kB of glyphs.
  • Skeletons, never spinners. Every fetch has a defined loading and offline state.
11

Two languages, verified

English and Hindi are complete: 444 keys in each, including every seeded advisory, city name, station name, AQI band, soil category and warning bulletin. The language picker also lists ten more Indian languages as downloadable packs — that list is a UI demonstration, and only English and Hindi are implemented.

The hard part was not the UI chrome, it was the data. Seeded prose used to render straight from the data file in English, so a Hindi sentence would switch language halfway through. Those strings now live in the dictionary with the data file's English as the fallback of record, and the build diffs the two copies.

What stays in English on purpose: live CPCB station names and live CAP bulletins, shown exactly as the upstream issued them. Plus acronyms and codes — IMD, CPCB, AQI, IST, RMC, state codes.

What the build refuses to ship

npm run check runs the type checker plus eight verification passes. These exist because each one corresponds to a bug that actually happened.

#CheckThe bug it prevents

5Contrast on 700 hourly-chip tint samplesThe tinted carousel dropping below AA at one hour

7CAP English in the dictionary matches the data fileRewording a bulletin and leaving the Hindi behind
7bAll 107 seeded strings have a translation and have not driftedExactly the half-English sentence described above
8Serverless routes have no relative importsA real production crash — see below

Check 8 has a story worth telling. /api/aqi imported a sibling file, which works locally but produced ERR_MODULE_NOT_FOUND on Vercel, because "type": "module" means emitted ESM and ESM cannot resolve an extensionless relative import. The fix was to inline the shared code so each route is self-contained; the check makes sure nobody reintroduces it. It was tested by putting the bug back and confirming the build failed.

13

Honest limits

Say these before a judge finds them. Every one has a reason and a route forward.

Is this a PWA? Can I install it?

Not yet. There is no web app manifest and no service worker. The original plan called for both; neither is built. It is a responsive web app that works well on a phone browser.

Does it work offline?

No — and be careful with the wording here. The seeded dataset means the app never shows a blank screen when a feed fails, and there is a defined stale-data state with an "updated X ago" timestamp. But with no network at all, the page itself will not load, because there is no service worker caching it. Demo-safe is not the same as offline-first.

Are my saved places and personas remembered?

Within a session, yes. Across a reload, no — nothing is persisted to localStorage yet. Given that broken favourites are a top complaint about the current app, this is the first thing to build next; it is roughly an hour of work.

Why are the forecast numbers not live?

IMD's forecast APIs require the calling server's IP to be whitelisted, which is a procurement timeline, not an engineering one. We wired everything that is reachable without it — CPCB air quality and NDMA's CAP warnings — and labelled everything else as seeded rather than presenting demo values as measurements.

Is there any traffic data on the commute card?

No, and the card does not imply one. It reads visibility, gusts and waterlogging risk — weather-side commute conditions. Traffic integration is a named next step, not a claim.

Pull-to-refresh — what actually refreshes?

Air quality does: the gesture clears the client cache and re-requests with cache: "reload". Warnings do not currently invalidate on pull; they refresh on their own five-minute cycle. That is a known gap.

Is the "updated X ago" timestamp real?

The live air-quality card shows CPCB's own publication timestamp, which is real. The header's overall data age is currently a fixed value, not a measured one.

14

Rapid fire

One-line answers to the questions most likely to come fast.

Why not just use OpenWeather for everything?

The brief is an IMD product. A homepage for India's national meteorological agency that quietly runs on an American commercial API would fail on the thing it is being judged for. We use OpenWeather for one map overlay and say so.

How is this personalized if there is no login?

Persona choice plus location plus time of day. No account, no tracking, no profile leaving the device — which is also why it needs no privacy policy to demo.

Why rule-based instead of machine learning?

Explainability is a hard requirement, not a preference. A judge asking "why is this card here" gets a sentence with the threshold and the reading in it. An ML ranker could not answer that, and there is no training data for eight personas anyway.

How many API calls does a screen load make?

Two to our backend — air quality for the selected city, and warnings once for all saved places. The map adds its own requests only when opened.

What happens if data.gov.in is down during this demo?

A five-second deadline and one four-second retry, then the card keeps its seeded value and relabels itself as seeded. You will see the badge change; nothing breaks.

How do you know the Hindi is complete?

The build fails if any key exists in one language and not the other, and separately if any of the 107 seeded strings loses its translation. It is not a manual check.

Could this scale to all of India?

The map's air layer already covers 154 cities in three zoom tiers. The persona and card logic is per-place and stateless, so scaling is a matter of the data source's coverage, not of our architecture.

What is the single most technically interesting thing here?

Pick one and own it. Reasonable answers: computing CPCB's Indian AQI from raw concentrations on our own server; the zoom-tiered map labels that prevent clutter by never drawing it; or a build that refuses to ship a contrast failure or a missing translation.
